observation target, not a default stop. The old inherited `deadlineAt` and
`reportDeadlineMinutes` setting are historical only. New optional

does not require extending a time allowance. The original timestamps remain.

behavior, not the corrected current default.

## Finite new-report work

The automatic maximum is the sum of remaining bounded finding attempts, not an
instruction to spend them. A 204-cold-finding control gets 1,224 maximum attempts
and uses exactly 408: one generation and one challenge per finding. Explicit caps
and previously persisted ledgers do not inherit a new allowance. Unchanged report
reimport, reload and settings changes are not a budget reset. Generation cannot
consume the last allowance owed to admitted mandatory challenges. One response
repair survives a generation-to-challenge yield; source follow-ups remain bounded.

Workers and shared local slots now actually support 1–32; default stays two.
Conflicting active project capacities are refused before reservation. Slots retain
FIFO, ownership, unknown-process protection, cancellation and quarantine. Local
source preparation precedes slot acquisition; the existing catalog/discovery
caches are shared, not verdicts. No weaker model or skipped challenge is used.
The 204-job control acquired one catalog and reached 16 concurrent fixed callbacks.
Separate actual-slot controls exercise four slots, FIFO and capacity conflicts;
the fixed 204 callback peak is not evidence of 16 remote provider requests.

The batch clock begins at import acceptance, before parse/index work. New journals
retain the original deadline across reload/Resume. Checks after capacity and
authorization awaits prevent late reservations; expiry aborts owned waits/work,
leaves a finite paused reason, and retains completed results. Shared old journals
are not migrated to new budgets/clocks. Continued or locally recovered output
after the acceptance window cannot count as an on-time batch pass. Receipts now
separate host preparation/scheduling (excluding capacity wait), capacity wait,
host invocation elapsed and local ingestion; these are elapsed boundaries, not
additive CPU profiles or sums of percentiles.

The controlled 204-job scenario uses artificial 2 ms generation/4 ms challenge
delays, actual parsing/gates/storage, and a 120-second test window. It exercises
all 408 stages and individual publication; no unfinished job is counted Ready.
The final-tree observation was 39.966 seconds from import acceptance (38.021 seconds
inside the coordinator). Earlier edited-tree observations were 29.649 seconds
(27.716 seconds inside) and, with concurrent local checking, 47.227 seconds
(45.504 seconds inside). None is real AI batch latency or a paired speed comparison. The workload is
204 copies of one source-complete guard allegation, not representative reasoning
complexity. Deadline-at-authorization, actual capacity-wait expiry, backoff/auth
failure, repair persistence, insufficient cap and existing crash/reopen controls
cover distinct failure boundaries. No source hashes/freshness checks were removed.

At an **assumed** 60 active seconds/request and 400 expected requests, the optimistic
service-work lower bound is 200/50/25 minutes at 2/8/16 slots. Minimum concurrency
is 14 for 30 minutes or 20 for 20 minutes, before local work, quotas, repairs and
dependent-path headroom. Actual account capacity and representative request time
remain unknown. The real 200-finding target is **unmeasured**, not passed. Existing
saved-open p95 2272.10 ms still misses 500 ms; no new comparable performance claim.
