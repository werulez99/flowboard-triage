# Independent source-first teaching reference

This reference was derived from the three complete synthetic Solidity sources and ordinary reports alongside this file, plus `../route-preparation/project/src/RouteBook.sol` and `../route-preparation/report.md`. No fixed response output, product run, provider call, transaction execution, or exploit reproduction was used. Lines below are original 1-based source lines relative to each fixture's `project` directory. The same author created the three small controls and their reference: this is independent of provider outputs, not an independently authored specification or blind benchmark. Source comments explicitly supply the intended rules for those controls; the route relies on visible source and Solidity internal-call/revert semantics. Conclusions apply only to these complete fictional programs.

## Time: duration and absolute deadline

- **Assessment and mechanism:** supported, within the integer clock model. `schedule` stores a duration while `ready` consumes the field as an absolute deadline. The start input is validated but never added to the duration.
- **Rule and basis:** `src/DeadlineWindow.sol:5` separately documents `deadline = startedAt + duration`; line 6 defines readiness against the absolute deadline. This explicit source specification supports the mismatch claim. The report alone is not the rule authority.
- **Actor and start constraints:** any caller may supply the modeled values; lines 11–12 require `0 < startedAt <= 1000000` and `0 < duration <= 1000`. Analyze `ready` after a completed `schedule`. No permission, real clock, or elapsed-time oracle is modeled.
- **Exact operations:** line 13 writes `deadline = duration`; line 17 returns `clock >= deadline`. `schedule` starts at line 10 and `ready` at line 16. Their relationship is a storage dependency, not a direct call.
- **Distinction:** a relative duration `d` and an absolute deadline `s + d` have different origins even when both use integer clock units. A positive start makes the actual threshold strictly earlier by `s`.
- **Same-input example:** for `(s, d, t) = (100, 20, 105)`, actual storage is 20 and actual readiness is `105 >= 20`, true. The documented storage is 120 and documented readiness is `105 >= 120`, false. In general the disagreement interval is `d <= t < s + d` for these same inputs.
- **Bounds and counterevidence:** the checks bound the documented sum by 1001000, so overflow does not explain the mismatch. Both comparisons agree below `d` and at or above `s + d`. The default unscheduled deadline and rescheduling policy are outside this report. No financial or deployment consequence follows from this toy model.

## Lifecycle: skipped update and unchanged checkpoint

- **Assessment and mechanism:** refuted. An inactive update returns before either storage write; omitting a write preserves the previous storage value.
- **Rule and basis:** `src/CheckpointBook.sol:5` documents preservation, with active-update behavior at line 6. Independently of that stated intent, the complete function body contradicts the report's concrete reset-to-zero claim.
- **Actor and start constraints:** any caller may choose `active`; consider `active=false`, a prior nonzero snapshot `S`, checkpoint `C`, and arbitrary supplied value `V`. The initializer at line 8 supplies an ordinary initial `S=7`, and line 9 defaults the checkpoint to zero.
- **Exact operations:** `update` begins at line 11. The inactive branch at line 12 returns at line 13; assignment at line 15 and checkpoint addition at line 16 are skipped. `readSnapshot` begins at line 19 and returns the stored snapshot at line 20. Its relation to `update` is a storage dependency, not a call.
- **Distinction:** not refreshing a historical snapshot is not clearing it. Whether a consumer needs a fresh snapshot is a separate requirement, not evidence of zeroing.
- **Same-input example:** from `(S, C) = (7, 0)` with `(V, active) = (99, false)`, the resulting pair remains `(7, 0)` and `readSnapshot` yields 7. The report predicts `(0, 0)` for exactly this same prior state and input. Symbolically the inactive path maps `(S, C)` to `(S, C)`.
- **Bounds and counterevidence:** an already-zero snapshot stays zero but does not establish a reset. An active call writes `V` and increases `C`, unless checked addition fails, in which case the writes revert. There is no hidden reset or other mutating function in this complete source. Freshness requirements beyond the documented preservation rule remain unspecified.

## Accounting: compare rounding with identical inputs

- **Assessment and mechanism:** the reported divide-first mechanism and universal subscale-zero consequence are refuted. The source computes a bounded product before applying integer division once.
- **Rule and basis:** `src/QuoteBook.sol:5` documents `floor(units * rate / 100)`. Line 6 excludes any independently audited economic policy. The source expression is sufficient to refute the report's specific operation order; it does not establish real-world rounding fairness.
- **Actor and start constraints:** any caller supplies unsigned `units=u` and `rate=r`; line 9 requires each to be at most 10000. The pure function has no initial storage dependency.
- **Exact operations:** `quote` begins at line 8; line 10 computes `product = units * rate`, then line 11 returns `product / 100`. Both operations belong to one function; there is no fabricated helper call.
- **Distinction:** actual `floor(u*r/100)` differs from alleged `floor(u/100)*r`. Both discard fractions, but at different points. Compare the same `u` and `r`, not two unrelated quotes.
- **Same-input example:** at `(u, r) = (9, 15)`, the product is 135, so actual output is 1 while the alleged divide-first output is 0. The real-valued reference is 1.35; actual truncation is 0.35, not a loss of the entire integer quote. Generally `100*q <= u*r < 100*(q+1)` for actual result `q`.
- **Bounds and counterevidence:** `u*r <= 100000000`, eliminating uint256 multiplication overflow under the guards. Products below 100 legitimately produce zero; exact multiples of 100 have no remainder. Rounding down differs from rounding up and may matter under a different specification, but no such requirement or financial consequence is supplied here.

## Route: repeated calls, returns, and final rejection

- **Assessment and mechanism:** refuted. Intermediate additions are reached before the approval guard, but a false final approval reverts the complete external invocation, including those writes.
- **Rule and basis:** Solidity internal calls share the external invocation's revert scope. The report expects rejection to preserve no intermediate writes, which agrees with the visible `require` at `src/RouteBook.sol:130`. The source contains no external call, catch boundary, or alternate mutator preserving the changes.
- **Actor and start constraints:** any caller may enter `commit` at line 9. The report fixes `approved=false`, `1 <= requestedThreshold=k <= 24`, and initial `(attempts=A, counter=C)` with `A+1` and `C+k+1` representable. Line 19 enforces the threshold bound. No external actor, deployment, or token interaction is modeled.
- **Exact operations:** line 10 adds one attempt; line 11 calls `_checkAmount`; line 12 calls `_preview` and captures its result as `delta`; lines 13 and 14 are distinct `_increment` occurrences with arguments `delta` and 1; line 15 calls `_requireApproval`. `_preview` begins at line 22, conditionally adds at lines 25, 29, 33, 37, 41, 45, 49, 53, 57, 61, 65, 69, 73, 77, 81, 85, 89, 93, 97, 101, 105, 109, 113 and 117, then returns `completed` at line 121. `_increment` begins at line 124, writes at line 125, and returns at line 126. `_requireApproval` begins at line 129 and rejects at line 130.
- **Distinction:** each internal `return` resumes its own caller. The first `_increment` return resumes `commit` before its second increment, and the second resumes before approval. Neither return makes prior writes durable. The preview result is available only after all 24 threshold conditions have been considered; the first reached condition is not the whole preview.
- **Same-input example:** with `(A, C, k, approved) = (2, 10, 3, false)`, the preview's first three additions produce `delta=3`; subsequent threshold conditions are false. Source evaluation temporarily reaches attempt 3, counter 13, then counter 14. The final false `require` leaves stored state `(2, 10)`, whereas the report predicts `(3, 14)` from these same inputs. Generally rejection leaves `(A, C)`, not `(A+1, C+k+1)`.
- **Bounds and counterevidence:** successful approval would preserve `(A+1, C+k+1)`, but that is a different input and cannot validate the false-approval claim. Invalid thresholds and arithmetic overflow reject earlier. The report's stated bounds exclude those earlier rejections so the final approval guard can be analyzed directly. This reference reasons from source; it makes no claim that a renderer or runtime successfully traversed every occurrence.
